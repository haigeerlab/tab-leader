# ADR-0004：用存活记录判断 Web Locks Leader 停摆，超时后 steal 接管

- 状态：已提议（随需求文档一起审批）
- 日期：2026-11-13

## 背景

浏览器冻结后台页面时，计时器停止、不派发 `pagehide`、持有的 Web Lock 不释放，其他标签页会一直排队。Web Locks 本身没有锁过期的概念。

## 决定

- Leader 每 `aliveInterval`（默认 60 秒）写一次 `${name}:alive` = `{ tab, at }`（R5）。
- 追随者每 `aliveInterval` 以及切回前台时检查，超过 `stallTimeout`（默认 180 秒）没更新就 `request(name, { steal: true })` 接管（R6）。
- 旧 Leader 写记录前先读，发现被替换就立即让出，不等 `AbortError`（R5）。
- 记录缺失、损坏、时间在未来，都不抢。

## 备选方案

- **用业务数据判断停摆**（前身实现的做法：看「上次发送」）：只适用于定时任务，不通用。
- **秒级心跳**（navigator.locks polyfill 的做法：每秒心跳、约 3 秒判死）：后台计时器被节流到每分钟一次时会误判，导致反复易主，还会频繁写 localStorage。
- **不处理冻结**：在 Android 等会冻结后台页的环境里，工作会无限期停摆。

## 影响

- 没有 localStorage 时无法接管（已知限制）。
- 180 秒阈值意味着冻结后最多约 4 分钟（阈值 + 一个检查间隔）才接管；需要更快的业务可以调小，代价是误判风险上升。
- 解冻后到发现被替换之间有极短窗口，写入已知限制。
