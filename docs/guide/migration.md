# 从自研实现迁移

很多项目已经有一份自己写的「多标签页只让一个去做」的实现，常见的是 Web Locks 加 localStorage 租约，或者只用 localStorage。本文说明怎么换成本库，并在换包那次发版里保持新旧标签页互相认得、不重复执行。

> 行为细节以需求文档 [spec/tab-leader.md](../../spec/tab-leader.md) 为准，存储格式的兼容承诺见 [ADR-0003](../adr/0003-name-as-key-and-record-compat.md)。

## 1. 先对照存储

本库把 `name` **原样**用作 Web Locks 的锁名和 localStorage key 的前缀，不加任何库自己的前缀：

| 用途 | 锁名或 key | 记录格式（JSON） |
|---|---|---|
| Web Locks 档的锁 | `name` | — |
| 租约档的租约 | `${name}:lease` | `{ "tab": string, "gen": number, "exp": number }`，`exp` 是过期时刻（毫秒时间戳） |
| Web Locks 档的存活记录 | `${name}:alive` | `{ "tab": string, "at": number }` |
| `createTabInterval` 的上次运行记录 | `${name}:last` | `{ "at": number, "id": string }`，`id` 是当时 `key()` 的返回值，没有 `key` 时为 `""` |
| 启动时检测存储是否可用 | `${name}:probe` | 写入后立即删除 |

拿你的实现逐项对照，结果分三种情况：

| 情况 | 怎么做 |
|---|---|
| 锁名、key 和格式都能对上 | 用原来的名字作 `name`。新旧实现共用同一把锁、同一份记录，换包那次发版不会多出 Leader，间隔也不会被打断 |
| 只有锁名对得上 | 用原来的锁名作 `name`。Web Locks 档仍然互斥；租约档和上次运行记录按下面第 2 节的规则处理 |
| 都对不上 | 换一个新名字，干净切换。新旧标签页在过渡期里各选各的，可能各做一次，业务要能容忍（见第 3 节） |

## 2. 记录格式不一致时会怎样

本库读到无法识别的记录时，不会报错：

- **租约**：识别不了的租约当作「没有人持有」，本库会写入自己的租约。因此**租约档里新旧实现格式不同就不互斥**，过渡期可能出现两个 Leader。
- **存活记录**：识别不了或不存在时，**永远不算停摆**。旧实现不写存活记录，本库的追随者也就不会去抢旧实现的 Leader；旧 Leader 被冻结时，要等它关闭才会换人，和迁移前一样。
- **上次运行记录**：识别不了时，本标签页按「没有记录」处理，当上 Leader 后立即运行一次，并用新格式覆盖。所以换包后第一次可能提前运行一次，之后恢复正常间隔。

## 3. 新旧实现混开

发版后，用户已经打开的标签页还在跑旧代码，新打开的跑新代码，两者会共存一段时间：

| 两边的实现 | 结果 |
|---|---|
| 都用 Web Locks，锁名相同 | 只有一个 Leader（浏览器保证），不管它跑的是新代码还是旧代码 |
| 都用租约，key 和格式相同 | 和只有新实现时一样尽力互斥 |
| 租约 key 或格式不同 | 不互斥，过渡期可能各有一个 Leader |
| 上次运行记录格式相同 | 新旧实现共用间隔，不会提前运行 |
| 上次运行记录格式不同 | 两边各算各的间隔，过渡期可能多运行几次 |

不管哪一种，只要业务要求「绝对不能重复」，都应该在后端去重或做幂等，见 [README 的保证程度](../../README.md#保证程度)。

## 4. API 差异的常见写法

自研实现的接口各不相同，下面是迁移时最常遇到的几处差异：

| 自研实现里常见的写法 | 本库 | 说明 |
|---|---|---|
| 创建即开始 | 先 `createTabLeader(...)`／`createTabInterval(...)`，再调 `start()` | 创建时不碰任何浏览器 API，SSR 下可以安全创建 |
| `checkNow()`、`trigger()` 之类「立即检查」 | `check()` | 只在是 Leader、并且到期或 `key` 变了时运行，**不强制运行** |
| `stop()`、`dispose()` | `destroy()` | 销毁后不能再 `start()`，需要时重新创建 |
| 身份函数抛错时退回某个默认值（例如 `'guest'`） | `key` 抛错时沿用上次的值，不会因此触发运行 | 需要原来的语义，就在 `key` 里自己捕获：`key: () => { try { return getIdentity() } catch { return 'guest' } }` |
| 任务失败后重试 | `run` 的同步异常和 Promise 拒绝都被吞掉，不重试 | 需要重试就在 `run` 里自己做 |
| 失去 Leader 时没有通知 | `onFollower` | 与 `onLeader` 严格交替 |

## 5. 迁移步骤

1. 按第 1 节对照锁名、key 和记录格式，决定 `name`。
2. 用本库替换自研实现，业务逻辑（什么时候算身份变了、任务本身做什么）留在你的代码里，通过 `key` 和 `run` 传进来。
3. 跑你原有的测试和构建。
4. 在真实浏览器里多开标签页验证：只有一个标签页在做事；关掉它，另一个接手；新旧代码的标签页混开时，按第 3 节的预期表现。
5. 上线后观察一段时间，确认没有重复执行、没有停摆。
