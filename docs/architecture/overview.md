# 架构概览

> 本文回答「为什么这样设计」。行为规则的唯一事实源是需求文档 [spec/tab-leader.md](../../spec/tab-leader.md)，这里引用它的规则编号（R*、I*），不复制规则原文。
> 设计来源（哪些借鉴自外部库、哪些来自前身实现的实测）见第 7 节。

## 1. 一句话

**用浏览器能提供的最强互斥手段选一个 Leader，手段不可用就降一档；任何一档里，Leader 都可能在不打招呼的情况下消失（关闭、崩溃、bfcache、冻结），所以每一档都要有「发现它消失 → 换人」的路径，并且换人时旧 Leader 留下的任务不能再起作用。**

## 2. 分层

```
┌──────────────────────────────────────────────────────────┐
│ createTabInterval（上层，可选）                            │
│   跨标签页限频：「上次运行」记录 + 严格间隔 + key 变化补跑    │
├──────────────────────────────────────────────────────────┤
│ createTabLeader（下层，通用）                              │
│   状态机 + 代次 + 生命周期事件 + onLeader / onFollower      │
├───────────────┬────────────────────┬─────────────────────┤
│ locks 档       │ lease 档           │ solo 档              │
│ Web Locks      │ localStorage 租约  │ 每个标签页都是 Leader │
│ + 存活记录      │ + storage 事件     │                      │
├───────────────┴────────────────────┴─────────────────────┤
│ env：window / document / navigator / localStorage / 时钟 / 计时器（可注入）│
└──────────────────────────────────────────────────────────┘
```

- **下层只回答「我是不是 Leader」**，不关心业务要做什么。业务在 `onLeader` 里启动工作，在 `onFollower` 里停手。
- **上层是最常见用法的薄封装**：「每 N 毫秒、全浏览器只跑一次」。它额外维护一条跨标签页共享的「上次运行」记录，这条记录让它在下层偶发双 Leader 的情况下也不会多跑（§5）。
- **env 层**把所有浏览器全局对象收口到一处：单测可以注入假环境，非浏览器环境（SSR）没有 `window` 时整个库什么也不做（R3）。

## 3. 降级链

```
start()
  │
  ├─ strategy 起始档 = auto ──┐
  │                           ▼
  │              navigator.locks 存在？ ──是──▶ locks 档
  │                           │否
  ├─ strategy = lease ───────▶▼
  │              localStorage 试写读删都成功？ ──是──▶ lease 档
  │                           │否
  └─ strategy = solo ────────▶▼
                            solo 档

运行中：locks 档的 request() 还没拿到锁就被拒绝 ──▶ 降到 lease，存储也不可用则 solo（R8a）
运行中：lease 档的存储读写开始抛错 ──▶ 降级为 solo（R11）
```

为什么是这个顺序：

| 档 | 互斥由谁保证 | 为什么排在这里 |
|---|---|---|
| locks | 浏览器（同源同名锁，进程级互斥） | 唯一真正原子的手段；标签页关闭或崩溃时浏览器自动释放锁 |
| lease | 自己（localStorage 读、写、等一下再读确认） | 旧浏览器（无 Web Locks）里唯一跨标签页可见、同步、普遍可用的存储；没有原子性，只能尽力 |
| solo | 无 | 存储也不可用时（隐私模式限制、WebView 禁用），宁可各自做，也不能停摆 |

为什么不用别的手段做中间档：

- **BroadcastChannel 选举**：Safari 15.4 以前没有，覆盖不了目标浏览器；而且基于消息的选举需要多轮通信和超时判断，在后台计时器被节流时比租约更容易误判。
- **IndexedDB 事务当锁**：各引擎对跨标签页事务的隔离行为不一，旧版 Safari 的 IndexedDB 问题较多，复杂度远高于 localStorage，收益不明显。
- **SharedWorker 当协调者**：iOS Safari 长期不支持，Android WebView 也不普遍。

## 4. 状态机与代次

```
            start()
   idle ─────────────▶ waiting ──当选──▶ leader
                         ▲  ▲              │
          失去 Leader ────┘  │              │ 让出 / 被抢 / 租约丢失
          (R7 R8 R11 R12)    └──────────────┘
                         │                  │
                pagehide │                  │ pagehide
                         ▼                  ▼
                       suspended ◀──────────┘
                         │ pageshow(persisted)
                         └──────▶ waiting

   任何状态 ──destroy()──▶ destroyed（不可再 start）
```

**代次（generation）是整个设计的地基**（R14）。浏览器会把任务延后执行：被节流的计时器、冻结期间排队的锁回调、恢复后才投递的 `AbortError`。如果旧任务回来时只看「当前状态」，就可能在已经换了 Leader 之后继续做事。所以：

- 每次失去 Leader、暂停、降级、销毁，代次 +1；
- 每个异步回调创建时记下当时的代次，执行时代次不一致就直接退出。

这比「取消所有计时器」更可靠，因为有些回调（锁回调、Promise 拒绝）根本取消不了。

**回调配对**（R15）：`onLeader`／`onFollower` 严格交替。业务可以放心地「onLeader 里开、onFollower 里关」，不用自己去重。

## 5. 冻结接管：最难的部分

浏览器冻结后台页面（Android Chrome 后台约 5 分钟就冻结；桌面 Chrome 的节能模式也会冻结）时：

- 页面的计时器全部停止；
- **不派发 `pagehide`**；
- 持有的 Web Lock **不释放**。

结果是其他标签页永远排在锁后面，工作停摆。原生 Web Locks 没有「锁过期」的概念，必须自己判断 Leader 是否还活着。

```
Leader（被冻结）                    追随者
──────────────                    ──────────────
写存活记录 {tab:A, at:t0}
（冻结，之后不再写）
                                   每 aliveInterval 检查一次
                                   now - t0 > stallTimeout？
                                   是 ──▶ request(name, {steal:true})
                                          成为 Leader，写 {tab:B, at:t1}
（解冻）
计时器先醒：写存活记录前先读，
发现 tab:B 且 at > 自己上次写入
──▶ 立即失去 Leader（R5）
随后 AbortError 到达 ──▶ 代次已变，忽略
```

几个关键取舍：

- **存活记录是通用的**，不依赖业务做了什么（R5）。前身实现用的是业务自己的「上次发送」记录来判断，只适用于定时任务。
- **阈值 180 秒**（R6）：桌面 Chrome 后台计时器最多延迟约 1 分钟，存活记录的实际间隔可能到 2 分钟；180 秒留出余量，不会把「只是被节流」误判为停摆，同时能在 Android 冻结后几分钟内接管。
- **找不到记录不抢**：记录缺失可能是迁移中的旧实现在当 Leader（它不写这条记录），宁可不接管，也不能误抢造成双 Leader。
- **R5 的先读后写**：冻结恢复后，计时器回调可能比 `AbortError` 先执行。读一下存活记录就能提前发现自己已经被替换，把双 Leader 窗口缩到最短。剩下的极短窗口写在已知限制里（spec §3.8）。

## 6. 租约档的竞态处理

localStorage 没有原子的「比较并交换」。租约档用三层防护把双 Leader 窗口压到很短：

1. **写后确认**（R10）：写入租约，等 `leaseConfirmDelay`（50 毫秒）再读回，仍是自己的才当选。两个标签页同时写时，后写的覆盖先写的，先写的读回时会发现不是自己。
2. **租约带代次**（R9）：`{ tab, gen, exp }`。同一标签页的旧代次任务读到的租约「不是自己的」，不会误以为还持有。
3. **使用前再核对**（I1 第 1 步）：上层每次运行前重新读租约，而不是相信缓存的 `isLeader`。

再加上上层的「上次运行」记录：即使两个标签页在极短时间内都认为自己是 Leader，后一个读到前一个刚写的记录，也不会再运行一次。

## 7. 设计来源

这个库的设计有两个来源：**外部开源库的思路**，以及**前身实现在实测和两轮代码审查里踩出来的坑**。我们只借鉴思路，不复制代码。

### 7.1 借鉴自外部开源库

> 各库的详细对比见[选型调研](../research/selection.md)。

| 来源 | 借鉴了什么 | 本库对应 |
|---|---|---|
| broadcast-channel（pubkey） | 「按能力探测自动选实现，Web Locks 优先，旧浏览器兜底」的总体思路；`isLeader`、`die()` 一类简洁的 API 命名 | 降级链（R2）；`isLeader`、`destroy()` |
| tab-election（dabblewriter） | 主动让出（`relinquishLeadership`）；用事件通知领导权变化（`leadershipchange`）；Hub 层「心跳断了就 `steal`」的接管方式 | `relinquish()`（R12）；`onLeader`／`onFollower`（R15）；停摆接管（R6）与它是同一类做法 |
| tabs-broadcast（Rovniy） | localStorage 回退时「Leader 定期刷新、过期判死、`pagehide` 时主动让出」 | 租约档（R9～R11）；`pagehide` 暂停（R13） |
| TanStack offline-transactions | 领导权变化回调做去重，避免重复通知 | 回调严格配对（R15） |
| @zukhruf/election | 任期号（epoch）：新 Leader 的任期总是压过旧的 | 与代次（R14）同一类做法 |
| navigator.locks（aermin）、leader-tab | **反面教训**：秒级甚至 50 毫秒的心跳，在后台计时器被节流到每分钟一次时会误判死亡、反复易主，还会频繁写存储 | 存活记录用 60 秒间隔、180 秒阈值（R5、R6）；租约 150 秒有效、60 秒续期 |
| 原生 Web Locks 规范 | `steal` 与 `AbortError` 的语义；锁随页面销毁自动释放 | R4、R6、R7 |

说明：停摆接管和代次是前身实现在实测中独立得出的（见 7.2），调研时才发现 tab-election 的 Hub 层、@zukhruf/election 有同类做法；这里如实列出，表示思路一致，不表示照搬。

### 7.2 来自前身实现的实测

这些都不是从外部库学来的，而是前身实现在真实浏览器里测出问题、经过审查后定下来的：

| 问题 | 解决方式 | 本库对应 |
|---|---|---|
| 被延迟执行的旧任务在换 Leader 后继续做事 | 代次校验 | R14 |
| Web Locks 的 Leader 被冻结后不释放锁，其他标签页永远排队 | 存活记录 + 超时抢锁 | R5、R6 |
| 被抢锁的旧 Leader 解冻后仍以为自己是 Leader | 收到 `AbortError` 让出并重新排队 | R7 |
| localStorage 不能原子地读、判断、写，两个标签页同时当选 | 写后确认 + 租约带代次 + 使用前核对 | R9、R10、I1 |
| 运行中存储突然不可用，所有标签页停摆 | 降级为 solo | R11 |
| 有 `navigator.locks` 但请求被立即拒绝（例如阻止所有网站数据），立即重试形成微任务死循环、卡死页面 | 没拿到锁就被拒绝视为 Web Locks 不可用，降到下一档，不重试 | R8a |
| 系统时钟调回后立即补跑 | 只重置计时起点 | I1 第 4 步 |
| 计时器提前触发导致提前运行 | 严格间隔，不留容差 | I2 |
| bfcache 恢复后重复启动、多套计时器 | `pageshow` 只在暂停状态下恢复 | R13 |
| 有 Web Locks 但没有 localStorage 的组合没人考虑过 | 分开检测两种能力 | R1、R2 |

## 8. 不做的事，以及原因

- **消息分发**（0.x 不做）：做了就等于再造半个 broadcast-channel，体积和测试面翻倍。需要的话，Leader 在 `onLeader` 里自己用 `BroadcastChannel` 或 `storage` 事件广播，示例见 [guide/recipes.md](../guide/recipes.md)。
- **给 `navigator.locks` 打补丁**：改写全局对象会影响页面里其他代码，违背「无全局副作用」。
- **判断 UA**：只做功能检测，新浏览器支持 Web Locks 后自动升档。
- **`AbortSignal`**：v1 不提供，`onFollower` 已经能表达「停手」。
